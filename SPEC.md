# SPEC.md — CSV ↔ LIFT Data Model

## Purpose and status

Defines the tables, keys, and column-naming/XML-structure conventions shared by lift2csv (LIFT → CSV) and csv2lift (CSV → LIFT).

This spec is the source of truth. When code and this document disagree, that is a bug: fix whichever is wrong, and update this document immediately whenever a design decision changes — do not let it drift out of sync with the code.

Built incrementally as design decisions are actually made through development; it does not speculate ahead of what is implemented. See [Not Yet Specified](#not-yet-specified) for what is deliberately left undesigned.

### LIFT model references

- [lift.rng](https://github.com/sillsdev/lift-standard/blob/master/lift.rng) — the LIFT RelaxNG schema, the authoritative definition of the format. It shows how flexible the spec actually is (most elements are optional, ordering and repetition are loosely constrained). Mind the version: the copy on `master` declares `version 0.15` and keys `<field>` by `@name`, while every file this project handles is `version 0.13`, where `<field>` is keyed by `@type` — which is what the code and fixtures assume. The 0.13 schema is the one FLEx validates against; it ships inside `SIL.Lift.dll` and is reproduced in full in the [Technical Notes](#lift-model-references)' Validation section. For every other element this spec cites — `note`/`field`/`form` cardinality, `interleave`d children, `extensible-content`, `grammatical-info`, `pronunciation`, `example`, `translation`, `span` — the two versions are identical, so a `lift.rng` citation below can be read in either.
- [Technical Notes on LIFT used in FLEx](https://downloads.languagetechnology.org/fieldworks/Documentation/Technical%20Notes%20on%20LIFT%20used%20in%20FLEx.pdf) — describes the practical subset FLEx actually produces/consumes day to day, which is what this project's fixtures and rules are modeled on.

## Conventions used throughout

Each table section ([Entry Table](#entry-table), [Sense Table](#sense-table), [Pronunciation Table](#pronunciation-table), [Example Table](#example-table)) states only its own column names and any deviation from these shared rules.

### Data handling

- **Dates**: `dateCreated`/`dateModified` are ISO 8601 UTC, format `YYYY-MM-DDTHH:MM:SSZ`, copied verbatim between LIFT and CSV — never regenerated or reformatted.
- **CSV reading/writing**: always read every column as character (`col_types = cols(.default = "c")`) and treat blank cells as `NA` (`na = ""`) on read; write with `format_csv(table, na = "")`. This avoids `readr`'s type-guessing silently corrupting round-trips (e.g. a numeric-looking custom field, or a blank cell becoming the literal string `"NA"`).
- **A column blank in every row is never emitted** (`drop_empty_columns()`/`format_table_csv()`, `R/table_csv.R`), whether it is a data-driven `<lang>`/`<type>`-keyed column (already created only when the document carries a value for it — see below) or a structural one (a key, an XML attribute, or a value column like `example_source`/`translation_type`). `NA` and `""` count alike, since the read/write convention above already makes them indistinguishable in the CSV. This is the same "don't emit nothing" rule applied at three granularities: an empty *table* is skipped by `--table-dir` ([csv2lift CLI shape](#csv2lift-cli-shape)), an empty *element* is never written ([Structural Rules](#structural-rules-csv2lift-direction)), and now an empty *column* is never written either — a zero-row table is simply the case where every column is empty, so the empty-table convention is this rule's consequence rather than a separate special case. The one place this can touch a value no other rule already excludes: `<form lang="x"><text/></form>` — a real `lang` with empty text — would prune its own `lang` column and lose the empty `<form>` on round-trip; no fixture has one (see [Not Yet Specified](#not-yet-specified)).
- **Column/element order**: within any multi-valued group (e.g. the `<form lang>` children of one `<field>`), order must reflect the order elements first appeared in the source LIFT document. Neither direction may re-sort (e.g. alphabetically) — this is what makes round-tripping faithful.
- **Writing system comes from the data, not from the field's declaration**: a column is created for whatever `lang` each `<form>`/`<gloss>` actually carries. Neither direction consults or enforces the writing system a field is *declared* with in FLEx, so a value whose `lang` disagrees with that declaration gets its own column and round-trips unchanged rather than being normalised or flagged. Real example: in `sena3.lift` the entry-level custom field `Plural` is declared "First Vernacular Writing System" and 518 of its 520 values are `lang="seh"`, but 2 are `lang="en"` — FLEx shows those in the same grid column, so they are easy to miss there. Those two entries get a blank `Plural_seh` and a filled `Plural_en`, and convert back to `<field type="Plural"><form lang="en">` exactly as they were. This is deliberate: the tool preserves what the export holds, and splitting by actual `lang` makes such anomalies *more* visible than the source application does. Correcting one is then a CSV edit (move the value to the `Plural_seh` cell) rather than a tool change. An entry carrying both writing systems for one field is representable too — it fills both columns and is written back as a single `<field>` with two `<form>` children in column order (see [Entry Table](#entry-table)) — though no fixture has one.
- **Inline `<span lang>` inside a multitext `<text>`**: LIFT allows a `<text>` to tag a stretch of its value as a different writing system with an inline `<span lang="...">` — typically an alternate-orthography form quoted inside an English note. This is carried in the CSV cell as the literal `<span lang="…">…</span>` tag, in both directions, with the text around it left exactly as it is and the span's `lang` as the only attribute represented. The two directions are asymmetric: on write, the literal text around a span is XML-escaped but the span tags themselves are not (`multitext_value()`/`set_multitext_text()`, `R/entry_helpers.R`). Escaping the whole value would turn spans back into text; escaping none of it produces invalid XML on the first bare `&`, which real note text has. This tool's round-trip is lossless regardless — but the [Technical Notes](#lift-model-references) note that FLEx itself is not: on import, "if a LIFT file has embedding in a Unicode field, … the text will be kept, but all span hierarchy will be lost including styles, writing systems, etc." That loss happens inside FLEx's own import step, not in this tool's conversion, so a span surviving csv2lift's output faithfully can still be flattened the moment FLEx reads it back in.
- **Column/element order across distinct attribute-keyed siblings**: the first-appearance rule above fixes order *within* one multi-valued group (e.g. the `<form lang>` children of one `<field>`), but not the relative order of distinct **attribute-keyed siblings** — custom `<field type>`s, and typed `<note type>`s ([Entry Table](#entry-table), [Sense Table](#sense-table)) — of the same parent. The CSV carries one global column order (first appearance across the whole document), while each parent's own element order is whatever the source LIFT happened to emit; when those disagree for a given parent, csv2lift re-orders that parent's siblings to match the global column order on the way back. Content is preserved; only sibling order changes (see [Not Yet Specified](#not-yet-specified) for the real figure). This does not apply to the example table's `translation_type` ([Example Table](#example-table)) — it is a plain value column, not an attribute-keyed sibling name, so there is nothing for it to reorder.
- **Redundant columns**: two different things get called redundancy here, and they are handled differently.
  - *Variation the source makes is not redundancy.* The `Plural_seh`/`Plural_en` case above is two columns holding two *different* values, and the rule there is that neither direction normalises them. It is not a precedent for carrying duplicates of the same value.
  - *Duplication the source itself contains is mirrored, not reconciled.* `example_source` and `note_reference_<lang>` ([Example Table](#example-table)) are one FLEx field written twice by its own exporter. Both columns are carried and neither direction picks a winner — but because nothing reconciles them, csv2lift **warns on stderr** when a row has both non-blank and disagreeing (`warn_on_reference_disagreement()`, `R/example_helpers.R`), then emits both unchanged. A CSV edit is the only way they ever diverge, and diverging silently would be worse than noisily. Deciding which value wins is not this tool's call.

### Column classification

- **One column per key per parent is schema-guaranteed, not a fixture accident.** `lift.rng` wraps `<note>`, `<field>`, and `<form>` in `zeroOrMore`, but each one's own content model then caps it per parent with a schematron assertion: `note-content` asserts "Notes should be of different types. There is only one note with a given type allowed in any parent element.", `field-content` the same for `<field type>`, and `multitext-content` asserts "Forms should be in different langs. There is only one form with a given lang allowed in any parent element." So `(type, lang)` uniquely identifies a note or custom field within one parent, and `lang` alone uniquely identifies a form — which is what makes the flat `note_<type>_<lang>`, `<field-type>_<lang>`, and one-column-per-writing-system schemes *representable*, not merely lucky. The `zeroOrMore` wrapper alone is not the cardinality signal; the element's own `<define>` is (see [the skill's note on reading `sch:assert`](.claude/skills/adding-a-lift-field/SKILL.md#understand-the-field-in-the-real-lift-model)). Invalid input violating these assertions is a separate matter — see [Not Yet Specified](#not-yet-specified).
- **Classification is by column name alone, and must match exactly between the two directions** — lift2csv's column naming and csv2lift's column parsing are the same rule read in opposite directions. Every table applies the same shape, in this order: fixed metadata names matched exactly; then reserved prefixes (`citation_`, `gloss_`, `definition_`, `general_note_`, `pronunciation_`, `media_label_`, `variant_`, `reversal_`, `etymology_`, `note_`, `example_`, `translation_`); then, on the entry, sense, etymology, and pronunciation tables, a fallback treating any remaining column as a custom `<field>`. The variant, example, and reversal tables have no fallback and hard-error instead ([Variant Table](#variant-table), [Example Table](#example-table), [Reversal Table](#reversal-table)).
- **Last-underscore splitting**: the custom-field fallback splits a column on its **last** underscore — field type is everything before, writing system everything after. Typed notes (`note_<type>_<lang>`) use the same split on the remainder after `note_`. A typed note's step must therefore precede the custom-field fallback, or `note_phonology_en` would be read as `<field type="note_phonology">`.
- **Known limitation of name-based classification** (accepted, not solved generally): a writing-system code containing an underscore will misclassify; so will a custom field named exactly like one of the reserved prefixes without its trailing underscore (`citation`, `note`, `gloss`, `definition`, `general_note`), or one whose type itself begins with `note_` (e.g. a field named `note_foo`), since typed notes share that prefix's namespace. On the [Example Table](#example-table), a writing system coded literally `source` or `type` would be swallowed by the `example_source`/`translation_type` exact-match metadata step, which must run before the `example_`/`translation_` prefix checks; no such code occurs in any fixture. The [Reversal Table](#reversal-table) has the identical exposure for `type` against `reversal_type`; no such code occurs there either. The same applies to every exact-match metadata name on the entry and sense tables (`entry_lift_id`, `entry_order`, `sense_order`, …): a custom field whose type/lang split happens to spell one of them exactly would be swallowed there too, since the metadata step runs first; no such field occurs in any fixture. The [Pronunciation Table](#pronunciation-table) has the identical exposure for `location` against its own exact-match metadata column, and for a custom field named exactly `pronunciation` or `media_label` without a trailing underscore (its two reserved prefixes without the underscore); no such case occurs in any fixture.
- **Typed notes are named `note_<type>_<lang>` at every level**, deliberately sharing one column name across the entry and sense tables ([Entry Table](#entry-table), [Sense Table](#sense-table)) rather than taking a per-level prefix (as untyped notes do, `note_` vs `general_note_`) or a FLEx-label-derived name. Two reasons:
  - The type vocabulary is open user data — a label-derived name like `phonology_note_en` can't be told apart from a custom field without hardcoding a closed list of known types.
  - Unlike untyped notes — where FLEx genuinely labels the entry and sense fields differently ("Note" vs "General Note") — a given type's FLEx label is the *same* at both levels (entry "Restrictions" and sense "Restrictions" are both just "Restrictions"). An artificial per-level prefix would mark a distinction FLEx does not make.

  The consequence is that one typed-note column name can occur on both tables — see the cross-table collision bullet below.
- **Column names are unique within a table, not across tables — a consumer joining the entry and sense CSVs must handle collisions itself.** This tool never joins them ([csv2lift CLI shape](#csv2lift-cli-shape) takes normalized per-table CSVs; joining them is downstream tooling's job), so nothing here resolves a name that occurs on both. `entry_id` is shared deliberately as the join key. Custom `<field-type>_<lang>` columns can collide if an entry-level and sense-level custom field happen to share a type and writing system. Typed notes collide by design — `note_<type>_<lang>` is deliberately the same name at every level (see above) — and this happens on real data: `sena3.lift` has 61 entry-level and 1 sense-level `restrictions` note, so both `_snaps/entry-table/sena3.csv` and `_snaps/sense-table/sena3.csv` carry a `note_restrictions_en` column with different content. A naive `left_join(senses, entries, by = "entry_id")` or `merge()` silently produces `note_restrictions_en.x`/`.y` (dplyr) or `_x`/`_y` (pandas) in that case. This is not a defect in the per-table CSVs to "fix" by renaming — the [Column Classification](#column-classification) rule above is what makes `note_` and `general_note_` distinct where the underlying FLEx fields actually are distinct; a shared name here means the fields genuinely are the same field at two levels.
- **`gloss_<lang>` on the [Etymology Table](#etymology-table) deliberately reuses the sense table's column name**, for the identical reason typed notes do: `<gloss>` is the same tag with the same FLEx label ("Gloss") at both levels, so an etymology-level prefix would invent a distinction FLEx does not make. `_snaps/sense-table/sena3.csv` and `_snaps/etymology-table/sena3-etymology-proto-and-comment.csv` both carry a `gloss_en` column with unrelated content — a downstream join's problem, not this tool's.

### Structural rules (csv2lift direction)

- **Canonical child element order is a readability convention, not a schema requirement**: `lift.rng` wraps element children in `<interleave>`, so nothing in LIFT fixes their order. Each table section states the order this tool always emits.
- **Empty optional elements are never emitted**: an element is written only when at least one of its columns is non-blank for that row. This covers entry-level lexical-unit/citation/note/typed note/morph_type/field ([Entry Table](#entry-table)), sense-level definition/note/typed note/field ([Sense Table](#sense-table)), and a whole `<pronunciation>` whose row has no form, `media_href`, custom field, or `location` value ([Pronunciation Table](#pronunciation-table)).
  **The rule stops at the row.** In a positionally-keyed table the row *is* the element's identity, so an all-blank row still emits its element: the [Example Table](#example-table) writes one `<example>` per row even when every column is blank, because dropping it would shift the position — and therefore the identity — of that example's surviving siblings. [Reversal Table](#reversal-table), [Etymology Table](#etymology-table), and [Variant Table](#variant-table) follow the same rule — for etymology and variant this is not hypothetical: 48 of 105 etymologies in `sena3.lift` carry no `<form>` at all, and one variant in `sena3-variant-multiple-and-blank-form.lift` carries no `<form>` either (its only content is a `morph-type` trait, read via the traits table's `owner = "variant"` — [Traits Table](#traits-table)), so a row with every column blank is the ordinary case for these tables, not an edge case. `<pronunciation>` ([Pronunciation Table](#pronunciation-table)) still omits a whole blank row rather than emitting `<pronunciation/>`; no fixture has ever exercised that branch, so it disagrees with the other four positionally-keyed tables on this point. This is a known inconsistency, not a considered design choice — see [Not Yet Specified](#not-yet-specified).
  **A required attribute is always emitted, even blank, unlike an optional one.** `etymology-content` has no `<optional>` around `@type`/`@source` (unlike every other attribute this codebase emits conditionally), so [Etymology Table](#etymology-table) writes both on every `<etymology>` regardless of content — the "omit when blank" half of this rule applies only to elements and to attributes `lift.rng` itself makes optional.
- **Foreign keys fail fast**: sense and pronunciation rows are attached to the entry whose existing `entry/@guid` matches their `entry_id` (entries have no other stable key), and example rows are attached to the sense whose `sense/@id` matches their `sense_guid`. A row matching no parent is a hard error — it is never silently dropped.
- **A primary key's uniqueness fails fast too**: `entry_lift_id` ([Entry Table](#entry-table)) is checked for duplicates, once, before any entry is emitted. A duplicate is a hard error rather than a silently-ambiguous file.
- **An unrecognised CSV under `--table-dir` fails fast, rather than silently dropping a table**: any `*.csv` directly in the given directory whose name matches no table in `R/table_registry.R` (e.g. a typo'd `sense.csv`) is a hard error — see [csv2lift CLI shape](#csv2lift-cli-shape).

## Entry table

Primary key: `entry_id` (= `entry/@guid`).

| Column                                             | LIFT source                              | Notes                                                                                   |
| --------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------- |
| `entry_id`                                         | `entry/@guid`                            | primary key                                                                             |
| `entry_lift_id`                                    | `entry/@id`                              | copied verbatim, never synthesized (see below); must be unique across the entry table   |
| `dateCreated`                                      | `entry/@dateCreated`                     |                                                                                         |
| `dateModified`                                     | `entry/@dateModified`                    |                                                                                         |
| `entry_order`                                      | `entry/@order`                           | copied verbatim, never regenerated from row position ([Data Handling](#data-handling)). FLEx emits it only on entries sharing a homograph number — 108 of 1462 in `sena3.lift` — so a blank here is normal, not missing data; per [Data Handling](#data-handling)'s empty-column rule, the column itself is absent entirely from lift2csv's output for any LIFT file where no entry carries `@order`. Named `entry_order` rather than `order` to match `entry_id` and to stay distinct from the sense-level `@order` attribute ([Sense Table](#sense-table)): this tool never joins the two tables ([Column Classification](#column-classification)'s cross-table collision bullet), but a consumer that does still needs the two `@order` values distinguishable, and a plain `order` on both tables would collide the moment they're combined |
| `morph_type`                                       | `entry/trait[@name='morph-type']/@value` | only first value if duplicated (warns)                                                  |
| `<lang>` (e.g. `seh`)                              | `entry/lexical-unit/form`                | one column per writing system found in the source                                       |
| `citation_<lang>`                                  | `entry/citation/form`                    | reserved prefix `citation_`                                                             |
| `note_<lang>`                                      | `entry/note[not(@type)]/form`            | reserved prefix `note_`; untyped note only (see below)                                  |
| `note_<type>_<lang>` (e.g. `note_restrictions_en`) | `entry/note[@type]/form`                 | typed notes (see [Column Classification](#column-classification)); `restrictions` is the only entry-level type in `sena3.lift`, with 61 |
| `<field-type>_<lang>`                              | `entry/field[@type]/form`                | custom fields                                                                           |

**Column classification algorithm** (see [Column Classification](#column-classification)):
1. Exact match against `entry_id`, `entry_lift_id`, `dateCreated`, `dateModified`, `entry_order`, `morph_type` → metadata.
2. Else matches `^citation_(.+)$` → citation, lang = capture group.
3. Else matches `^note_.+_[^_]+$` (i.e. at least two underscores after the `note_` prefix) → typed note. Must precede step 4, or a typed note's type would be read as part of the writing system — entry-level untyped and typed notes share the `note_` prefix, so their order is load-bearing in a way the sense table's is not ([Sense Table](#sense-table)).
4. Else matches `^note_(.+)$` → note (untyped), lang = capture group.
5. Else contains no underscore → lexical-unit, lang = column name.
6. Else → custom field.

`<note>` is read/written untyped (`[not(@type)]`) into `note_<lang>` and typed (`[@type]`) into `note_<type>_<lang>`, mirroring custom `<field>` handling. LIFT/FLEx reuses the `<note>` element for other, unrelated fields distinguished by `type` (e.g. `<note type="restrictions">` is FLEx's separate "Restrictions" field, not its generic "Note" field — confirmed against real FieldWorks-exported data, where filtering for the Note field in FLEx does not surface `restrictions`-typed notes).

`entry_lift_id` is stored verbatim rather than rebuilt from the headword, on the [Technical Notes](#lift-model-references) rather than a judgement call: `@id` is an opaque within-file handle whose only stated requirement is uniqueness — "Id fields can have any text as long as it is unique in the LIFT file" — and "any non-guid id will be converted to a guid during import", so there is no semantic content to keep in sync. `sena3.lift`'s ids all happen to equal headword + (`@order` or `""`) + `"_"` + `@guid` (1462/1462, headword = citation form when present else lexical-unit form), but that shape is an inherited WeSay convention the doc calls "normal", not a rule this tool relies on, checks, or reconstructs. Rebuilding it would also walk into FLEx bug LT-21075, which the same document flags twice: FLEx "will get error messages when finding main entries if the entry id contains most Unicode characters, such as U+0331 diacritic", in some cases hanging the import. `sena3.lift` carries 5 such ids of 1462 (precomposed `á`/`ú`; no combining marks), so this is risk inherited from the export, not created here — do not "fix" it by rewriting ids.

**csv2lift direction:**
- `id` is emitted verbatim from `entry_lift_id` when non-blank, never synthesized. `guid` is emitted from `entry_id` independently — FLEx treats `guid` as the true primary key and does not require `id` when `guid` is present ("There is an exception where the entry id is not needed if you have a guid attribute instead", "Entries also have a guid attribute which is used in FLEx as the primary ID") — so a CSV with no `entry_lift_id` column still converts, producing entries with `guid` but no `id`. This absent-column tolerance is load-bearing on two live paths, not just a historical accommodation: a hand-authored CSV that never had the column, and lift2csv's own output, which omits `entry_lift_id` entirely whenever every row's value would be blank ([Data Handling](#data-handling)'s empty-column rule) — though `entry_lift_id` is derived from other columns and non-blank whenever `entry_id`/headword data exists, so no fixture exercises that second path for this particular column.
- `entry_lift_id` must be unique across the entry table (its only documented requirement) — checked once before any entry is emitted, **not** that it still matches the headword or carries the guid as a suffix, both of which the documentation treats as convention rather than rule. A duplicate is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)).
- Emit `dateCreated`/`dateModified`/`guid`/`order` attributes only when non-blank, and `order` also when the `entry_order` column is absent entirely — which happens routinely now, not just on a legacy CSV: [Data Handling](#data-handling)'s empty-column rule means lift2csv's own output omits `entry_order` whenever no entry in the source LIFT file carries `@order` (108 of 1462 do in `sena3.lift`, so most single-entry fixtures produce no column at all). The `%in% names(row)` guard this requires is load-bearing on that ordinary path, mirroring the sense writer's `sense_order` guard ([Sense Table](#sense-table)).
- Canonical child element order ([Structural Rules](#structural-rules-csv2lift-direction)): `<lexical-unit>`, `<trait name="morph-type">`, `<citation>`, `<note>`, one `<note type=X>` per distinct note type, one `<field type=X>` per distinct field type — grouping every lang for that type into one `<note>`/`<field>` element, never one per lang — then `<pronunciation>` elements ([Pronunciation Table](#pronunciation-table)), then `<variant>` elements ([Variant Table](#variant-table)), then `<sense>` elements ([Sense Table](#sense-table)), then `<relation>` elements ([Entry-Relation Table](#entry-relation-table)), then `<etymology>` elements ([Etymology Table](#etymology-table)). Pronunciations, variants, senses, entry-relations, and etymologies are appended by later passes over their own tables, so what fixes their position is `R/table_registry.R`'s row order (registry row order *is* attach order). Variants are registered right after pronunciations, matching `lift.rng`'s own declared order for `entry-content`'s children (`<pronunciation>`, `<variant>`, `<sense>`, …) — nothing about *correctness* depends on this, since `attach_variants_to_lift()` only ever looks entries up by guid, same as pronunciations. Entry-relations are registered after reversals (which attach to senses, not entries), matching `lift.rng`'s own declared order for `entry-content`'s children (`<relation>` follows `<sense>` and precedes `<etymology>`) — likewise not a correctness dependency, since `attach_entry_relations_to_lift()` only ever looks entries up by guid. Etymologies are registered last, after entry-relations, for the same reason — real FLEx output does not actually follow this (`<etymology>` is emitted *before* `<sense>` in every entry that has both, in every fixture), so this tool's emitted order deliberately disagrees with the source here, the same kind of divergence [Sense Table](#sense-table) documents for `<example>` vs `<note>`.
- Within `<lexical-unit>`, `<citation>`, `<note>`, and each typed `<note>`/`<field>`, `<form lang>` children are emitted in the CSV's own column order ([Data Handling](#data-handling)) — never re-sorted.
- Zero input rows still produce a valid `<lift version="0.13" producer="..."/>` root with no entries.

## Sense table

Primary key: `sense_guid` (= `sense/@id`, or `subsense/@id` for a subsense's own row — see `parent_sense_guid` below). Foreign key: `entry_id`.

**One row per `<sense>` and per `<subsense>`.** `lift.rng` gives `<subsense>` (`sense/subsense`) the identical content model as `<sense>` itself (`subsense-content` is `sense-content`, verbatim) — the same element, nested one level deeper, rather than a distinct shape — so a subsense's own row uses every column below exactly as a top-level sense would, with one addition: `parent_sense_guid`, blank for a top-level sense and filled with the immediate parent's own `sense_guid` for a subsense (a subsense's parent can itself be a subsense — `lift.rng` permits arbitrary nesting depth, though `sena3.lift`'s 8 subsenses are all exactly one level deep, and only that depth is exercised by any fixture). This is a self-referencing foreign key into this same table, the first of its kind in this data model.

| Column                                                                   | LIFT source                     | Notes                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------ | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sense_guid`                                                             | `sense/@id`                     | primary key                                                                                                                                                                                                                                                                                                                                                                                               |
| `entry_id`                                                               | (parent `entry/@guid`)          | foreign key → entry table                                                                                                                                                                                                                                                                                                                                                                                |
| `sense_order`                                                            | `sense/@order`                  | copied verbatim, never regenerated from row position ([Data Handling](#data-handling)). FLEx emits it only on the senses of multi-sense entries — in `sena3.lift`, on all 446 such senses and on none of the 1271 single-sense ones — so a blank here is normal, not missing data; per [Data Handling](#data-handling)'s empty-column rule, the column itself is absent entirely from lift2csv's output for any LIFT file where no sense carries `@order`. Named `sense_order` rather than `order` to match `sense_guid` and to stay distinct from the entry-level `@order` attribute ([Entry Table](#entry-table)): this tool never joins the two tables ([Column Classification](#column-classification)'s cross-table collision bullet), but a consumer that does still needs the two `@order` values distinguishable, and a plain `order` on both tables would collide the moment they're combined |
| `grammatical_info`                                                       | `sense/grammatical-info/@value` | LIFT permits at most one `grammatical-info` per sense (`lift.rng` wraps it in `<optional>` with no `zeroOrMore`/`oneOrMore`); confirmed by real data — no fixture, including the 1717-sense `sena3.lift`, has ever had more than one. A `<grammatical-info>`'s own nested `<trait>`s (e.g. `inflection-feature`) are a separate table — see [Traits Table](#traits-table)                                                                                                                                                                        |
| `parent_sense_guid`                                                      | (structural — the immediate parent's own `sense_guid`, not an XML attribute) | blank for a top-level `<sense>`; filled for a `<subsense>`, disambiguating it from the case above ([Data Handling](#data-handling)'s empty-column rule drops this column entirely from a LIFT file with no subsenses at all). `sena3.lift`'s 8 subsenses each carry `grammatical-info`/`gloss`/`definition`/`note` in the same shapes a top-level sense does — see the column rows above and below, all shared verbatim |
| `gloss_<lang>` (e.g. `gloss_en`)                                         | `sense/gloss[@lang]`            | one column per writing system found in the source; `<gloss>` itself carries `lang` and a `<text>` child, unlike the `<form>`-wrapped multitext elements                                                                                                                                                                                                                                                    |
| `definition_<lang>` (e.g. `definition_en`)                               | `sense/definition/form`         | one column per writing system found in the source                                                                                                                                                                                                                                                                                                                                                         |
| `general_note_<lang>`                                                    | `sense/note[not(@type)]/form`   | reserved prefix `general_note_`; untyped note only. FLEx's sense pane labels this field "General Note", distinct from the entry-level "Note" field ([Entry Table](#entry-table)) and from the typed sense notes (Phonology Note, Grammar Note, etc.) — hence a different reserved prefix from entry-level notes rather than reusing `note_`                                                                                           |
| `note_<type>_<lang>` (e.g. `note_phonology_en`, FLEx's "Phonology Note") | `sense/note[@type]/form`        | typed notes ([Column Classification](#column-classification)). `sena3.lift`'s sense-level types are `phonology` (199), `sociolinguistics` (126), `grammar` (31), `source` (31), `semantics` (18), `restrictions` (1)                                                                                                                                                                                                                                   |
| `<field-type>_<lang>`                                                    | `sense/field[@type]/form`       | custom fields                                                                                                                                                                                                                                                                                                                                                                                             |

**Column classification algorithm** (see [Column Classification](#column-classification)):
1. Exact match against `sense_guid`, `entry_id`, `sense_order`, `grammatical_info`, `parent_sense_guid` → metadata.
2. Else matches `^gloss_(.+)$` → gloss, lang = capture group.
3. Else matches `^definition_(.+)$` → definition, lang = capture group.
4. Else matches `^general_note_(.+)$` → note, lang = capture group.
5. Else matches `^note_.+_[^_]+$` (i.e. at least two underscores after the `note_` prefix) → typed note. Order vs step 4 is free (the two prefixes are disjoint, unlike at entry level — see [Entry Table](#entry-table)); order vs step 6 is load-bearing (see [Column Classification](#column-classification)).
6. Else → custom field.

**lift2csv direction:** `sense_table()` captures every `<sense>` child per entry — exercised by the real `sena3.lift` fixture, which has entries with up to 6 senses. `extract_sense_metadata()` (`R/sense_helpers.R`) recurses into each sense's own `./subsense` children (depth-first: a sense/subsense's own row is immediately followed by its own subsenses' rows, in turn followed by theirs — matching document order at any nesting depth, though only depth 1 is exercised). The multitext stages (`gloss`, `definition`, `general_note`, typed notes, custom fields) read over `.//entry/sense | .//subsense` rather than `.//entry/sense` alone, for the same reason: these helpers key purely by a node's own `@id`, so widening the node list is the only change needed to cover subsense-owned data too. `example_table()` ([Example Table](#example-table)) is likewise widened, since a `<subsense>` can carry its own direct `<example>` child; `reversal_table()`, `sense_relation_table()`, and `trait_table()`'s sense/grammatical-info-owned extraction are **not** widened — no fixture has a subsense-owned reversal, relation, or trait, so extending those would be building ahead of real data ([AGENTS.md's Core Principles](AGENTS.md#core-principles)).

**csv2lift direction:** implemented by `attach_senses_to_lift(doc, sense_table)` (`R/csv2lift_sense.R`), using `classify_sense_columns()` (`R/sense_helpers.R`) to classify columns per the algorithm above. LIFT uses `id` (not `guid`) for `<sense>`/`<subsense>`; it is emitted from `sense_guid`, omitted if blank. `order` is emitted from `sense_order` and omitted when blank *or when the column is absent entirely* — which happens routinely now, not just on a legacy CSV: [Data Handling](#data-handling)'s empty-column rule means lift2csv's own output omits `sense_order` whenever no sense in the source LIFT file carries `@order` (446 of 1717 do in `sena3.lift`, so a single-sense fixture produces no column at all). The `%in% names(row)` guard this requires is load-bearing on that ordinary path, mirroring the entry writer's `dateCreated`/`dateModified` guard ([Entry Table](#entry-table)). Canonical child order ([Structural Rules](#structural-rules-csv2lift-direction)): `<grammatical-info>`, `<gloss>` (one per non-blank `gloss_<lang>` column, added directly under `<sense>`), `<definition>`, `<note>` (from `general_note_<lang>` columns), one `<note type=X>` per distinct note type, one `<field type=X>` per distinct field type — grouping every lang for that type into one `<note>`/`<field>` element, never one per lang — then `<subsense>` elements, if any (attached within this same pass, right after a row's own fields above — see below), then `<relation>` elements ([Sense-Relation Table](#sense-relation-table)), then `<example>` elements ([Example Table](#example-table); inserted *before* a `<subsense>` rather than appended, when the sense has one — see below), then `<reversal>` elements ([Reversal Table](#reversal-table)). One `<sense>` is attached per matching row, in CSV row order — proven by the `sena3-multiple-senses-per-entry` fixture.

**A row with a non-blank `parent_sense_guid` is attached as `<subsense>` instead of `<sense>`, and to whichever existing `<sense>` or `<subsense>` node has that guid as its own id, not to the entry.** Computed once per table (`is_subsense_row`, vectorised over the whole `parent_sense_guid` column) rather than per row. The parent lookup — `.//*[self::sense or self::subsense][@id='...']` — is a hard error on no match ([Structural Rules](#structural-rules-csv2lift-direction)), same as every other foreign key. This relies on a genuinely new ordering rule this table alone has: **a parent row must precede its subsense's row** in the CSV, since the parent must already exist as an XML node before its subsense can attach to it. `extract_sense_metadata()`'s own depth-first read order guarantees this for reader output (a row is always immediately followed by its own subsenses' rows); a hand-reordered CSV that violates it fails the same "not found" error a bad `entry_id`/`sense_guid` would, rather than being silently dropped. A single walk over the table in row order handles nesting to any depth for free — no separate pass per depth level is needed, since by the time a subsense's own row is reached, its parent (whether a top-level sense or another subsense processed earlier in the same walk) is already attached.

Sense-relations, examples, and reversals are each appended by a later pass over their own table ([Sense-Relation Table](#sense-relation-table), [Example Table](#example-table), [Reversal Table](#reversal-table)), exactly as pronunciations and senses are appended to `<entry>` ([Entry Table](#entry-table)) — what fixes their position among a sense's children is the order `R/table_registry.R`'s rows are attached in (registry row order *is* attach order, per the file's own opening comment), not this list. This means the emitted order can disagree with FLEx's own child order, and for `<example>` it usually does when a sense has both: FLEx puts `<example>` *before* `<note>` (412 senses in `sena3.lift` are `grammatical-info, gloss, example, note`), but this tool emits it after `<note>` and after any `<subsense>` the sense's own row already carries (below) — it is only "always last" when the sense has no subsense of its own. `lift.rng` wraps sense children in `<interleave>` ([Structural Rules](#structural-rules-csv2lift-direction)), so this is permitted — content is preserved, only position changes — but it is the first case in this data model where the emitted order deliberately disagrees with the source rather than mirroring it. `<reversal>` does not have this problem: it registers after `examples`, matching `lift.rng`'s own declared order for `sense-content`'s children, and no fixture has a sense with both an example and a reversal to prove or disprove it against real FLEx output either way. `<relation>` has the identical exposure `<example>` does: `lift.rng` declares it *before* `<note>` in `sense-content`, but this tool's `sense-relations` registry row is positioned after `senses` (a correctness dependency — sense nodes must exist first) and so after `attach_senses_to_lift()`'s own `<note>` emission, which always runs first regardless; `sena3.lift`'s own senses with both a relation and a note confirm this re-ordering happens in practice, not just in principle.

**`<subsense>` is `lift.rng`'s declared last child of `sense-content`, and real FLEx output agrees** — unlike `<example>`/`<relation>` above, which this tool already, separately, emits after `<note>` regardless of source order. Since `attach_senses_to_lift()` attaches a subsense as part of its own registry pass, entirely before `examples`'/`reversals`' own later passes start, simply *appending* a sense's own example/reversal (the ordinary path, above) would always land it after that sense's subsense (and after everything the subsense itself contains) even when the source had it the other way around. `sena3.lift` entry `e0aa351f-…` forces this: its sense has both its own `<example>` and a `<subsense>` that itself has a nested `<example>` — appending would put the subsense's nested example, and everything else in the subsense, ahead of the parent's own example, contradicting the source. `attach_examples_to_lift()` ([Example Table](#example-table)) therefore inserts a sense's own example *before* any existing `<subsense>` child instead of appending, when the sense has one — confirmed lossless against this exact entry and against the full `sena3.lift` corpus ([`plans/full-corpus-roundtrip-check.md`](plans/full-corpus-roundtrip-check.md)). `attach_reversals_to_lift()` is not given the identical treatment: no fixture has a sense with both a reversal and a subsense, so there is nothing to build or test it against ([Not Yet Specified](#not-yet-specified)). Nor is `attach_sense_relations_to_lift()` — and unlike reversal, which simply lands after everything else regardless, a sense combining a subsense with a sense-relation would see its `<relation>` attached (appended) *before* `<example>`'s own insert-before-subsense logic runs, since `sense-relations` registers ahead of `examples`; that pulls `<example>` to a position *before* `<relation>` too, not just before `<subsense>`. This is an artifact of two independent, individually-correct rules interacting in a combination no fixture forces, not a designed ordering — see [Not Yet Specified](#not-yet-specified).

## Pronunciation table

One row per `<entry>/<pronunciation>`. Foreign key: `entry_id`. **No primary key** — `<pronunciation>` carries no `id` or `guid` in LIFT, unlike `<entry>` (`guid`) and `<sense>` (`id`), so the only thing identifying a pronunciation is its position. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling): neither direction may re-sort, and re-ordering the CSV's rows re-orders the emitted elements.

| Column                       | LIFT source                          | Notes                                                                               |
| ----------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------- |
| `entry_id`                   | (parent `entry/@guid`)               | foreign key → entry table                                                           |
| `pronunciation_<lang>`       | `entry/pronunciation/form`           | reserved prefix `pronunciation_`; one column per writing system found in the source |
| `media_href`                 | `entry/pronunciation/media/@href`    | the audio filename; at most one per row (see below)                                 |
| `media_label_<lang>`         | `entry/pronunciation/media/label/form` | reserved prefix `media_label_`; the media's own caption, keyed to the same `<media>` `media_href` came from (see below) |
| `<field-type>_<lang>`        | `entry/pronunciation/field[@type]/form` | custom fields; `cv-pattern` and `tone` are FLEx's own declared pronunciation-level fields, but nothing restricts this to those two |
| `location`                   | `entry/pronunciation/trait[@name='location']/@value` | the only pronunciation-level trait name seen in real data; only first value if duplicated (warns) — see below for why this is a dedicated column rather than a row in the [Traits Table](#traits-table) |

**Column classification algorithm** (see [Column Classification](#column-classification)): exact match against `entry_id`, `media_href`, `location` → metadata; else matches `^pronunciation_(.+)$` → form, lang = capture group; else matches `^media_label_(.+)$` → media label, lang = capture group; else → custom field, split on the last underscore (same known limitation as [Entry Table](#entry-table)/[Sense Table](#sense-table)'s fallback). Unlike [Variant Table](#variant-table)/[Example Table](#example-table)/[Reversal Table](#reversal-table), this ends in the custom-field fallback rather than a hard error, since pronunciation-level `<field>` is now read and written.

**lift2csv direction:** implemented by `pronunciation_table(LIFT_file)` (`R/pronunciation_table.R`). `lift.rng` permits zero or more `<media>` per `<pronunciation>`, but a row holds a single `media_href`/`media_label_<lang>` set; a pronunciation with more than one `<media>` warns on stderr (naming the entry) and keeps the first, mirroring `extract_single_trait()`'s handling of duplicate traits — `extract_first_media()` (`R/pronunciation_helpers.R`) picks that one node once and both `media_href` and `media_label_<lang>` are read from it, so the two can never disagree about which media element is "first". A pronunciation with no `<media>` yields a blank `media_href` (and no label columns), and one with no `<form>` children yields blank form columns — both occur in `zhi-note-and-phonology-notes.lift`, whose pronunciations are media-only. Custom `<field type>` children (`cv-pattern`, `tone`) are read the same way etymology-level fields are, type-keyed via `extract_pronunciation_multitext_with_attribute()`. The `location` trait is read via `extract_single_pronunciation_trait()`, the pronunciation-level analogue of `extract_single_trait()` ([Entry Table](#entry-table)'s `morph_type`) — a dedicated column rather than a [Traits Table](#traits-table) row, because every real instance seen (`zhi-flex_lift_2026-09-29.lift`) is the same trait name, at most one per pronunciation, the identical shape `morph-type` has at the entry level; a second, distinct pronunciation-level trait name would need this decision revisited (see [Not Yet Specified](#not-yet-specified)). A lexicon with no pronunciations produces an empty CSV, as `lift2csv.R --table senses` does for a lexicon with no senses.

**csv2lift direction:** implemented by `attach_pronunciations_to_lift(doc, pronunciation_table)` (`R/csv2lift_pronunciation.R`), using `classify_pronunciation_columns()` (`R/pronunciation_helpers.R`). Canonical child order ([Structural Rules](#structural-rules-csv2lift-direction)): within each `<pronunciation>`, `<form lang>` children come first, then `<media href>` (with its own optional `<label>` child, populated from `media_label_<lang>` only when at least one is non-blank), then one `<field type=X>` per distinct custom-field type, then the `<trait name="location">`, matching every real occurrence seen. The row-omission rule ([Structural Rules](#structural-rules-csv2lift-direction)) now checks all four channels — a row with no transcription, no audio file, no custom field, and no `location` value produces no `<pronunciation>` at all, not just a row with no form and no media.

**Why a table of its own** rather than columns on the entry table: `lift.rng` wraps `pronunciation` in `<zeroOrMore>`, and real exports use it. `zhi-two-pronunciations-with-audio-and-ipa.lift` has one entry with two pronunciations whose forms share a single writing system (`zhi-fonipa-x-etic`: `tsēn` and `tsʼēn`). Two values, one writing system, one entry cannot be represented in one row under any column-naming scheme.

## Variant table

One row per `entry/variant`. Foreign key: `entry_id`. **No primary key** — `<variant>` carries no `id` or `guid` in LIFT (it may carry an optional `@ref` to another entry — see [Not Yet Specified](#not-yet-specified) — but no fixture has one), the same situation as `<pronunciation>` ([Pronunciation Table](#pronunciation-table)): the only thing identifying a variant is its position among an entry's `<variant>` children. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling).

| Column | LIFT source | Notes |
| --- | --- | --- |
| `entry_id` | (parent `entry/@guid`) | foreign key → entry table |
| `variant_<lang>` (e.g. `variant_seh`) | `entry/variant/form` | reserved prefix `variant_`; one column per writing system found in the source. `sena3.lift` uses only `seh`, with up to 8 variants on one entry |

**Column classification algorithm** (see [Column Classification](#column-classification)): exact match against `entry_id` → metadata; else matches `^variant_(.+)$` → form, lang = capture group; else → hard error, as with pronunciation ([Pronunciation Table](#pronunciation-table)), example ([Example Table](#example-table)), and reversal ([Reversal Table](#reversal-table)) — variant-level `<field>`/`@ref`/`<pronunciation>`/`<relation>` aren't read or written at all ([Not Yet Specified](#not-yet-specified)).

**lift2csv direction:** implemented by `variant_table(LIFT_file)` (`R/variant_table.R`), over `.//entry/variant`. `extract_variant_multitext()` (`R/variant_helpers.R`) is keyed by the variant's document position, mirroring `extract_pronunciation_multitext()`/`extract_reversal_multitext()`/`extract_etymology_multitext()`. A variant with no `<form>` at all yields a row with every `variant_<lang>` blank rather than being dropped — not hypothetical: `sena3.lift` has one such variant (entry `d7a3eba8-…`), whose only content is a `morph-type` trait, read via the traits table's `owner = "variant"` ([Traits Table](#traits-table)).

**csv2lift direction:** implemented by `attach_variants_to_lift(doc, variant_table)` (`R/csv2lift_variant.R`), using `classify_variant_columns()` (`R/variant_helpers.R`). A row's `entry_id` is looked up against `.//entry[@guid='...']`; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. **`<variant>` is emitted unconditionally, even for an all-blank row**, the same positional-identity reasoning as `<example>`/`<reversal>`/`<etymology>` — and, like etymology, real data forces the question rather than leaving it hypothetical: the all-blank variant above must still round-trip to an (empty) `<variant/>` element, or its position relative to any other variant on that entry would shift. `attach_variants_to_lift()` is registered in `R/table_registry.R` right after `pronunciations`, matching `lift.rng`'s own declared child order for `entry-content` ([Entry Table](#entry-table)) — nothing about *correctness* requires this order, since lookups are by entry guid alone.

**Why a table of its own** rather than columns on the entry table: `lift.rng` wraps `variant` in `<zeroOrMore>`, and real data uses it heavily — `sena3.lift` has 168 variants across 131 entries, with up to 8 on one entry, so no `variant_<lang>`-only scheme (nor an indexed `variant_1_<lang>`/`variant_2_<lang>` one — see [the skill's rejection of indexed columns](.claude/skills/adding-a-lift-field/SKILL.md#decide-where-it-lives-a-column-or-a-table-of-its-own)) could hold one entry's set in a single row.

## Example table

One row per `sense/example` or `subsense/example`. Foreign key: `sense_guid` (a subsense's own `sense_guid`, per [Sense Table](#sense-table)'s `parent_sense_guid`, when the example hangs off a subsense rather than a top-level sense). **No primary key** — `<example>` carries no `id` or `guid` in LIFT, the same situation as `<pronunciation>` ([Pronunciation Table](#pronunciation-table)) one level deeper: the only thing identifying an example is its position among all `sense/example` elements in the document. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling).

| Column | LIFT source | Notes |
| --- | --- | --- |
| `sense_guid` | (parent `sense/@id`) | foreign key → sense table |
| `example_source` | `example/@source` | FLEx's "Reference" field; see below for its relationship to `note_reference_<lang>`. Absent entirely from lift2csv's output when no example in the LIFT file carries `@source` ([Data Handling](#data-handling)'s empty-column rule) |
| `example_<lang>` (e.g. `example_seh`) | `example/form` | reserved prefix `example_`; one column per writing system found in the source |
| `translation_type` | `example/translation/@type` | a plain value column, not part of a column name — treated as one Translation with one Type per Example, unlike typed notes/fields' open set of sibling elements to key a column name on. This is an assumption, not something the FLEx UI guarantees: a screenshot of real FLEx data entry shows two Translation controls both left at "Free translation," so the UI itself can produce two same-typed translations on one example, contradicting `lift.rng`'s own schematron ("Translations should be of different types") — whether by design or a UI quirk is unclear. `lift.rng` wraps `translation` in `zeroOrMore` regardless, and the [Technical Notes](#lift-model-references) say outright that "any number of translation elements can be present in an example element" — so more than one translation, same-typed or differently-typed, is something this column shape cannot hold (it warns and keeps the first, as below). Absent entirely from lift2csv's output when no example's translation carries `@type` ([Data Handling](#data-handling)'s empty-column rule) — this does not weaken the type-only-translation guarantee below (a *present* `translation_type` column with a filled cell and blank `translation_<lang>` cells still round-trips); the column only disappears when every row's type is blank too |
| `translation_<lang>` (e.g. `translation_pt`) | `example/translation/form` | reserved prefix `translation_`; the translation text |
| `note_reference_<lang>` | `example/note[@type]/form` | reuses the typed-note scheme (see [Column Classification](#column-classification)), which is named `note_<type>_<lang>` at every level; `reference` is the only example-level type in `sena3.lift`, with 744 |

**Column classification algorithm** (see [Column Classification](#column-classification)): exact match against `sense_guid`, `example_source`, `translation_type` → metadata; else matches `^note_.+_[^_]+$` → typed note; else matches `^example_(.+)$` → example form, lang = capture group; else matches `^translation_(.+)$` → translation form, lang = capture group; else → hard error, as with pronunciation ([Pronunciation Table](#pronunciation-table)) — example-level `<field>` isn't read or written at all ([Not Yet Specified](#not-yet-specified)). The metadata step must run first: `example_source` matches the example-form pattern and `translation_type` matches the translation-form pattern, so both would otherwise misclassify with `lang="source"`/`lang="type"`.

**`@source` and `note[@type="reference"]` are the same FLEx field ("Reference") written twice by the exporter** — in `sena3.lift` `example_source` is non-blank on exactly the 744 examples with a `note_reference_<lang>`, and the two values are byte-identical in all 744. Both are still carried as separate columns rather than collapsed into one: collapsing would have to invent a `lang` for the note on write, which the source actually carries, and this tool's stance is to preserve what the export holds rather than reconcile apparent redundancy ([Data Handling](#data-handling)'s redundant-columns rule — note that the `Plural_seh`/`Plural_en` case is *not* the precedent for this, since those two columns hold different values). If a user edits one column and not the other, the two are emitted independently and can disagree; csv2lift warns on stderr when that happens and emits both unchanged, rather than reconciling them.

**lift2csv direction:** implemented by `example_table(LIFT_file)` (`R/example_table.R`), over `.//entry/sense/example | .//subsense/example` — the second clause covers a subsense's own direct example (1 occurrence in `sena3.lift`, entry `e0aa351f-…`'s subsense `abc99545-…`), now that `<subsense>` has a row of its own in the sense table ([Sense Table](#sense-table)). `.//subsense` matches any nesting depth on its own, so no deeper union is needed. `extract_example_translation()` (`R/example_helpers.R`) warns on stderr and keeps the first `<translation>` when an example has more than one (1 occurrence in `sena3.lift`, entry `d5cb3ce5-…`) — `lift.rng`'s own schematron on `translation-content` asserts "Translations should be of different types", so this is invalid LIFT that FLEx emitted, not a shape the CSV declines to model. The warning names what's discarded (each dropped translation's own `@type` and form text), not just that something was — `sena3.lift`'s one real case drops two same-typed but unrelated translations ("tolerant"/"tolerante" kept, "broken hearted"/"coração quebrado" discarded), so "using the first" alone would read as handled rather than as lost data. A translation whose `@type` is set but which has no `<form>` children (18 of 193 in `sena3.lift`) still produces a row with `translation_type` filled and every `translation_<lang>` blank, rather than being dropped.

**csv2lift direction:** implemented by `attach_examples_to_lift(doc, example_table)` (`R/csv2lift_example.R`), using `classify_example_columns()` (`R/example_helpers.R`). A row's `sense_guid` is looked up against `.//*[self::sense or self::subsense][@id='...']` — matching a `<subsense>` too, for the same reason the read direction does; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. **`<example>` is emitted unconditionally, even for an all-blank row** — this is the one deviation from [Structural Rules](#structural-rules-csv2lift-direction)'s "empty optional elements are never emitted": since identity here is purely positional, dropping a blank example would shift the index of its surviving siblings, and six senses in `sena3.lift` interleave blank and non-blank examples. `<translation>` is emitted whenever `translation_type` is non-blank *or* any `translation_<lang>` is non-blank, so a type-only translation round-trips rather than being silently dropped. Canonical child order within `<example>`: `<form>`, `<translation>`, `<note type="reference">` — this matches the source's own child order in every shape observed, unlike the sense-level position of `<example>` itself ([Sense Table](#sense-table)). `attach_examples_to_lift()` must be called **after** `attach_senses_to_lift()` in `scripts/csv2lift.R`: `<sense>`/`<subsense>` nodes do not exist before then, so this is a correctness dependency, not a readability convention ([CLI Shape](#csv2lift-cli-shape) lists the required CLI ordering).

**A sense's own example is inserted *before* any existing `<subsense>` child, rather than appended, when the sense has one** — see [Sense Table](#sense-table)'s own discussion of why (`lift.rng` declares `<subsense>` sense-content's last child, and `attach_senses_to_lift()` always attaches it before this table's own pass starts). Confirmed lossless against `sena3.lift` entry `e0aa351f-…`, whose sense has both its own example and a subsense with a nested example of its own, and against the full corpus ([`plans/full-corpus-roundtrip-check.md`](plans/full-corpus-roundtrip-check.md)).

**Why a table of its own** rather than columns on the sense table: `lift.rng` wraps `example` in `<zeroOrMore>`, and real exports use it heavily — `sena3.lift` has 1296 examples across 1717 senses, with up to 5 on one sense.

## Reversal table

One row per `sense/reversal`. Foreign key: `sense_guid`. **No primary key** — `<reversal>` carries no `id` or `guid` in LIFT, the same situation as `<pronunciation>` ([Pronunciation Table](#pronunciation-table)) and `<example>` ([Example Table](#example-table)): the only thing identifying a reversal is its position among all `sense/reversal` elements in the document. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling). All of this table's fixture data comes from the `zhi` fixtures — `sena3.lift` has none.

| Column | LIFT source | Notes |
| --- | --- | --- |
| `sense_guid` | (parent `sense/@id`) | foreign key → sense table |
| `reversal_type` | `reversal/@type` | a plain value column, not part of a column name, unlike typed notes/fields' open set of sibling elements — `reversal-content` has no schematron cap on `(type, lang)` uniqueness the way `note-content`/`field-content` do, and real data exercises this directly: one sense in `zhi-two-pronunciations-with-audio-and-ipa.lift` has two `<reversal type="en">` elements holding different text ("guest", "visitor"), so a `reversal_<type>_<lang>`-style column scheme could not hold both. Absent entirely from lift2csv's output when no reversal in the LIFT file carries `@type` ([Data Handling](#data-handling)'s empty-column rule) |
| `reversal_<lang>` (e.g. `reversal_en`) | `reversal/form` | reserved prefix `reversal_`; one column per writing system found in the source |

**Column classification algorithm** (see [Column Classification](#column-classification)): exact match against `sense_guid`, `reversal_type` → metadata; else matches `^reversal_(.+)$` → form, lang = capture group; else → hard error, as with pronunciation ([Pronunciation Table](#pronunciation-table)) and example ([Example Table](#example-table)) — reversal-level `<field>` isn't read or written at all ([Not Yet Specified](#not-yet-specified)). The metadata step must run first: `reversal_type` matches the reversal-form pattern too, so it would otherwise misclassify with `lang="type"`.

**lift2csv direction:** implemented by `reversal_table(LIFT_file)` (`R/reversal_table.R`), over the direct-child axis `.//entry/sense/reversal` — this deliberately excludes `sense/subsense/reversal`, unlike [Example Table](#example-table)'s own axis, which now covers `subsense/example`: no fixture has a `<reversal>` on a subsense, so widening this one would be building ahead of real data ([Not Yet Specified](#not-yet-specified)), not a limitation of `<subsense>` support itself ([Sense Table](#sense-table)).

**csv2lift direction:** implemented by `attach_reversals_to_lift(doc, reversal_table)` (`R/csv2lift_reversal.R`), using `classify_reversal_columns()` (`R/reversal_helpers.R`). A row's `sense_guid` is looked up against `.//sense[@id='...']`; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. **`<reversal>` is emitted unconditionally, even for an all-blank row**, the same deviation from [Structural Rules](#structural-rules-csv2lift-direction)'s "empty optional elements are never emitted" as `<example>` — since identity here is purely positional, dropping a blank row would shift the index of its surviving siblings. No fixture has an all-blank reversal or interleaved blank/non-blank reversals on one sense to prove this against, unlike `<example>`'s six interleaving senses in `sena3.lift`; the choice follows the table's own identity model (row order carries it) rather than evidence, and deliberately does **not** copy `<pronunciation>`'s opposite default, which [Structural Rules](#structural-rules-csv2lift-direction) already calls a known inconsistency rather than a considered one. `attach_reversals_to_lift()` must be called **after** `attach_senses_to_lift()` in `scripts/csv2lift.R`: `<sense>` nodes do not exist before then ([CLI Shape](#csv2lift-cli-shape) lists the required CLI ordering, via `R/table_registry.R`'s row order).

**Why a table of its own** rather than columns on the sense table: `lift.rng`'s `reversal-content` has no uniqueness assertion on `(type, lang)` at all (unlike `note-content`/`field-content`), so two same-typed reversals on one sense are schema-legal, not just a fixture accident — and, as noted above, real data already has one.

## Sense-relation table

One row per `sense/relation`. Foreign key: `sense_guid`. **No primary key** — `<relation>` carries no `id` or `guid` in LIFT, the same situation as `<reversal>`/`<example>` one level up in this table's own parent: the only thing identifying a relation is its position among all `sense/relation` elements in the document. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling). `sena3.lift` has 44, up to 2 on one sense.

| Column | LIFT source | Notes |
| --- | --- | --- |
| `sense_guid` | (parent `sense/@id`) | foreign key → sense table |
| `relation_type` | `relation/@type` | required by `relation-content` (no `<optional>` wrapper) — always emitted, even as `""`, the same required-attribute shape as [Etymology Table](#etymology-table)'s `@type`/`@source`. `sena3.lift`'s values are `Synonyms` (40) and `Antonym` (4) |
| `relation_ref` | `relation/@ref` | required for the same reason as `relation_type`. Copied verbatim in both directions — unlike [Entry-Relation Table](#entry-relation-table)'s `relation_ref`, no id/guid translation is needed here, because `sense/relation/@ref` already targets the other sense's own `@id`, which is always guid-shaped ([Sense Table](#sense-table)) |

**No column-classification step**, the same shape as [Traits Table](#traits-table): these two columns (plus the foreign key) are the whole schema, so there is nothing to pivot into per-language columns and no reserved-prefix/custom-field-fallback scheme applies. `sense/relation/trait` and `sense/relation/field` aren't read or written at all ([Not Yet Specified](#not-yet-specified)) — none occur in `sena3.lift`'s 44 sense-relations.

**lift2csv direction:** implemented by `sense_relation_table(LIFT_file)` (`R/sense_relation_table.R`), over the direct-child axis `.//entry/sense/relation` — this deliberately excludes `sense/subsense/relation`, for the same reason [Reversal Table](#reversal-table) excludes `sense/subsense/reversal`: no fixture has one, so widening this axis would be building ahead of real data ([Not Yet Specified](#not-yet-specified)), not a limitation of `<subsense>` support itself ([Sense Table](#sense-table)).

**csv2lift direction:** implemented by `attach_sense_relations_to_lift(doc, sense_relation_table)` (`R/csv2lift_sense_relation.R`). A row's `sense_guid` is looked up against `.//sense[@id='...']`; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. `relation_ref` is *also* resolved against `.//sense[@id='...']` before writing — a ref naming no sense in the table is a hard error too, rather than a `<relation>` written with a dangling reference: nothing else in this tool validates a same-document cross-reference this way (every other foreign key points from one table's row back to its own declared parent), but the FLEx documentation warns that unresolvable relation references can corrupt an entire import ("the result will probably be very bad" for Collection-type relations with unresolvable references), so failing fast here is a deliberate departure from "only validate declared parents," not an oversight. `attach_sense_relations_to_lift()` must be called **after** `attach_senses_to_lift()` in `scripts/csv2lift.R`: `<sense>` nodes do not exist before then, so this is a correctness dependency, not a readability convention ([CLI Shape](#csv2lift-cli-shape) lists the required CLI ordering, via `R/table_registry.R`'s row order). `<relation>` is positioned among a sense's children wherever `attach_senses_to_lift()`'s own emitted columns end and the registry's externally-attached tables begin — in `sena3.lift`, that puts it *after* `<note>` rather than before, disagreeing with `lift.rng`'s own declared `sense-content` order (`relation` before `note`); this is the identical, already-documented divergence [Sense Table](#sense-table) describes for `<example>` vs `<note>`, not a new one.

**Why a table of its own** rather than columns on the sense table: `lift.rng` wraps `relation` in `<zeroOrMore>` under both `<sense>` and `<entry>`, and real data uses it at both levels (see also [Entry-Relation Table](#entry-relation-table)) — `sena3.lift` has senses with 2 relations, so no single-column scheme could hold both.

## Etymology table

One row per `entry/etymology`. Foreign key: `entry_id`. **No primary key** — `<etymology>` carries no `id` or `guid` in LIFT, the same situation as `<pronunciation>` ([Pronunciation Table](#pronunciation-table)): the only thing identifying an etymology is its position among an entry's `<etymology>` children. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling). `lift.rng` caps `<etymology>` at one per entry no tighter than `<zeroOrMore>`, and real data never exceeds that — 105/105 entries with an etymology in `sena3.lift` have exactly one — but nothing in the schema promises it stays that way, so this is a table rather than a column, mirroring `<pronunciation>`.

| Column | LIFT source | Notes |
| --- | --- | --- |
| `entry_id` | (parent `entry/@guid`) | foreign key → entry table |
| `etymology_type` | `etymology/@type` | required by `etymology-content` (no `<optional>` wrapper) — always emitted, even as `""`, unlike every other attribute this tool writes conditionally. `sena3.lift`'s values are `borrowed` (98) and `proto` (7) |
| `etymology_source` | `etymology/@source` | required for the same reason as `etymology_type`. Always `""` in `sena3.lift`, so [Data Handling](#data-handling)'s empty-column rule drops the column entirely from lift2csv's own output — carried internally regardless, since csv2lift must still emit the (possibly blank) attribute on every `<etymology>` |
| `etymology_<lang>` (e.g. `etymology_seh`) | `etymology/form` | reserved prefix `etymology_`; one column per writing system found in the source. 48 of 105 etymologies in `sena3.lift` have no `<form>` at all — the etymon is recorded only in a custom field instead — so a blank `etymology_<lang>` on an otherwise non-blank row is the ordinary case |
| `gloss_<lang>` (e.g. `gloss_en`) | `etymology/gloss` | same column name as the sense table's `gloss_<lang>` ([Column Classification](#column-classification)'s cross-table collision bullet) — `<gloss>` carries `lang` directly on itself, no `<form>` wrapper, mirroring sense-level gloss rather than the `<form>`-wrapped shapes. 10 of 105 etymologies carry one, in `en`/`pt` |
| `<field-type>_<lang>` | `etymology/field[@type]/form` | custom fields, exactly as at entry/sense level. `sena3.lift`'s etymology-level types are `languagenotes` (99) and `comment` (46, always alongside `languagenotes`) |

**Column classification algorithm** (see [Column Classification](#column-classification)): exact match against `entry_id`, `etymology_type`, `etymology_source` → metadata; else matches `^etymology_(.+)$` → form, lang = capture group; else matches `^gloss_(.+)$` → gloss, lang = capture group; else → custom field, split on the last underscore (same known limitation as [Entry Table](#entry-table)/[Sense Table](#sense-table)'s fallback). Unlike [Pronunciation Table](#pronunciation-table)/[Reversal Table](#reversal-table), this ends in the custom-field fallback rather than a hard error, since etymology-level `<field>` is read and written.

**lift2csv direction:** implemented by `etymology_table(LIFT_file)` (`R/etymology_table.R`), over `.//entry/etymology`. `extract_etymology_multitext()` (`R/etymology_helpers.R`) is keyed by the etymology's document position (mirroring `extract_pronunciation_multitext()`/`extract_reversal_multitext()`) and serves both `<form>` and `<gloss>`, since both carry `lang` on the node the xpath itself returns. `extract_etymology_multitext_with_attribute()` is the same position-keyed adaptation of `extract_multitext_with_attribute()` for the custom `<field type>` children.

**csv2lift direction:** implemented by `attach_etymologies_to_lift(doc, etymology_table)` (`R/csv2lift_etymology.R`), using `classify_etymology_columns()` (`R/etymology_helpers.R`). A row's `entry_id` is looked up against `.//entry[@guid='...']`; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. **`<etymology>` is emitted unconditionally, even for an all-blank row** ([Structural Rules](#structural-rules-csv2lift-direction)), the same positional-identity reasoning as `<example>`/`<reversal>` — and unlike those two, real data forces the question: 48 of 105 etymologies have no `<form>`, so omitting a blank row is not a hypothetical this table can defer. `@type`/`@source` are likewise always written, even as `""`, since both are schema-required rather than optional. Canonical child order within `<etymology>`: `<form>`, then `<gloss>`, then `<field>` — this matches the source's own child order in every shape observed, unlike `lift.rng`'s own declared order for `etymology-content` (which lists its `<field>`-bearing `extensible-content` first). `attach_etymologies_to_lift()` is registered after `entry-relations` in `R/table_registry.R`, matching `lift.rng`'s own declared order for `entry-content`'s children (`<etymology>` is its last child, after `<relation>` — [Entry Table](#entry-table)).

**Why a table of its own** rather than columns on the entry table: `lift.rng` wraps `etymology` in `<zeroOrMore>` with no schematron cap tighter than that (unlike `note-content`/`field-content`'s `(type, lang)` uniqueness assertions). No fixture currently has two on one entry, so this is a schema-permitted case this tool defends against rather than one real data has forced — the same status `<pronunciation>`'s two-per-entry case had before `zhi-two-pronunciations-with-audio-and-ipa.lift` was captured.

## Entry-relation table

One row per `entry/relation`. Foreign key: `entry_id`. **No primary key** — `<relation>` carries no `id` or `guid` in LIFT, the same situation as `<etymology>` ([Etymology Table](#etymology-table)) one level up: the only thing identifying a relation is its position among an entry's own `<relation>` children. Row order is therefore load-bearing in both directions, per [Data Handling](#data-handling). `sena3.lift` has 31, up to 3 on one entry.

| Column | LIFT source | Notes |
| --- | --- | --- |
| `entry_id` | (parent `entry/@guid`) | foreign key → entry table |
| `relation_type` | `relation/@type` | required by `relation-content` (no `<optional>` wrapper) — always emitted, even as `""`, the same required-attribute shape as [Etymology Table](#etymology-table)'s `@type`/`@source`. `sena3.lift`'s values are `_component-lexeme` (23, FLEx's "Complex Forms"), `Etymological` (4), `Compare` (4) |
| `relation_ref` | `relation/@ref` | required for the same reason as `relation_type`. **Holds the target entry's guid, not the raw `@id` string** — `entry/relation/@ref` targets another entry's `@id` ("References to entries and senses within the LIFT file use the id string" — [Technical Notes](#lift-model-references)), not its `@guid`, confirmed against all 31 refs in `sena3.lift`; copying it verbatim would embed another row's headword and guid in a text field, while every other FK in this tool is a guid ([Structural Rules](#structural-rules-csv2lift-direction)). Translated entry `@id` → target guid on read (built once per document, over every entry, since a ref can target an entry that only ever appears as someone else's target) and target guid → `entry_lift_id` on write, by looking the target entry up by guid and reading back the `@id` it was written with |
| `relation_order` | `relation/@order` | copied verbatim, never regenerated from row position ([Data Handling](#data-handling)). In `sena3.lift`, present only on `_component-lexeme` relations (23/31) — where it records the order of an entry's own components — and absent on `Etymological`/`Compare`; absent entirely from lift2csv's output when no relation in the LIFT file carries `@order` ([Data Handling](#data-handling)'s empty-column rule) |

**No column-classification step**, the same shape as [Traits Table](#traits-table)/[Sense-Relation Table](#sense-relation-table): these three columns (plus the foreign key) are the whole schema, so there is nothing to pivot into per-language columns and no reserved-prefix/custom-field-fallback scheme applies. `entry/relation/field` and the optional `<usage>` child `relation-content` allows aren't read or written at all ([Not Yet Specified](#not-yet-specified)). `entry/relation/trait` (`complex-form-type`, `is-primary`, `variant-type`) is read and written via the [Traits Table](#traits-table)'s `owner = "entry-relation"`, not as a column here — the same "a table of its own attaches traits through the traits table, not its own columns" shape [Variant Table](#variant-table) already has.

**lift2csv direction:** implemented by `entry_relation_table(LIFT_file)` (`R/entry_relation_table.R`), over `.//entry/relation`. A ref that resolves against no entry's `@id` in the document warns on stderr (naming the entry and the raw ref string) and leaves `relation_ref` blank, rather than failing the whole read over one row — not hypothetical in general (a ref can outlive the entry it named), never observed in `sena3.lift` (all 31 resolve), but real in a FLEx 9.3.10.1452 export: 9 entries there carry a dangling `<relation type="_component-lexeme" ref=""/>`, its target apparently deleted after export — see `zhi-entry-relation-blank-ref.lift`.

**csv2lift direction:** implemented by `attach_entry_relations_to_lift(doc, entry_relation_table)` (`R/csv2lift_entry_relation.R`). A row's `entry_id` is looked up against `.//entry[@guid='...']`; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. **A blank `relation_ref` is written back verbatim as `ref=""`, with a warning, rather than resolved** — the one deliberate exception to "every foreign key resolves or hard-errors" this table makes, since a blank ref is real source data (lift2csv's read-direction paragraph above) rather than a lookup failure csv2lift itself needs to catch; treating it as the latter is what used to crash the whole conversion over one dangling relation. The `relation_ref` column can be absent entirely rather than merely blank — when every relation in the document has a blank ref, [Data Handling](#data-handling)'s empty-column rule drops the column before csv2lift ever sees it — so the check is `!("relation_ref" %in% names(row)) || !has_nonblank(row$relation_ref)`, not just an `NA` check. Otherwise, `relation_ref` is resolved as before, against `.//entry[@guid='...']` before writing, and if the target entry has no `entry_lift_id` to write as `@ref` (a blank/absent `entry_lift_id` column — [Entry Table](#entry-table)), that is a hard error too, since `relation/@ref` requires a target id: nothing else in this tool validates a same-document cross-reference this way (every other foreign key points from one table's row back to its own declared parent), but the FLEx documentation warns that unresolvable relation references can corrupt an entire import ("the result will probably be very bad" for Collection-type relations with unresolvable references), so failing fast here is a deliberate departure from "only validate declared parents," not an oversight — the identical reasoning [Sense-Relation Table](#sense-relation-table) applies to its own `relation_ref`. `@type`/`@ref` are always written, even as `""`/blank would be invalid, since both are schema-required rather than optional; `@order` is emitted only when non-blank *and* the `relation_order` column is present, mirroring `entry_order`'s/`etymology_type`'s column-absence guard. `attach_entry_relations_to_lift()` is registered after `reversals` in `R/table_registry.R`, matching `lift.rng`'s own declared order for `entry-content`'s children (`<relation>` follows `<sense>`) — attach_entry_relations_to_lift() only ever looks entries up by guid, so like `variants`/`etymologies` this is a readability choice, not a correctness one.

**Why a table of its own** rather than columns on the entry table: `lift.rng` wraps `relation` in `<zeroOrMore>` under both `<entry>` and `<sense>`, and real data uses it at both levels (see also [Sense-Relation Table](#sense-relation-table)) — `sena3.lift` has an entry with 3 relations, so no single-column scheme could hold them.

## Traits table

One row per sense-owned `<trait>`, grammatical-info-owned `<trait>`, variant-owned `<trait>`, or entry-relation-owned `<trait>` — the four attachment points a `<trait>` element uses today. Foreign keys: `entry_id` (always filled) and `sense_guid` (filled for the `sense`/`grammatical-info` owners; blank for `variant`/`entry-relation`, neither of which involves a sense at all — a `<variant>` and an `entry/relation` both hang directly off `<entry>`). **No primary key.** For the `sense`/`grammatical-info` owners, position isn't what carries a row's identity: `(sense_guid, owner, trait_name, trait_value)` already disambiguates it, since a sense has at most one `<grammatical-info>`. For `variant`/`entry-relation`, `sense_guid` is blank on every row regardless of which entry or which variant/relation it belongs to, so `owner_index` (below) is load-bearing there in a way it isn't for the other two owners — `(entry_id, owner, owner_index, trait_name, trait_value)` is what disambiguates a variant- or entry-relation-owned row.

| Column | LIFT source | Notes |
| --- | --- | --- |
| `entry_id` | (parent `entry/@guid`) | foreign key → entry table |
| `sense_guid` | (parent `sense/@id`) | foreign key → sense table — the trait's owning sense, when the owner is `sense` or `grammatical-info`; blank for `variant`/`entry-relation` |
| `owner` | (structural, not an XML attribute) | `sense` (`sense/trait`), `grammatical-info` (`sense/grammatical-info/trait`), `variant` (`entry/variant/trait`), or `entry-relation` (`entry/relation/trait`) |
| `owner_index` | (reserved for `sense`/`grammatical-info`; load-bearing for `variant`/`entry-relation`) | blank for `sense`/`grammatical-info`: a sense has at most one `<grammatical-info>` ([Sense Table](#sense-table)), so `sense_guid` alone already identifies it for both. For `variant`, the variant's 1-based position among its entry's own `<variant>` siblings — `<variant>` has no id/guid of its own ([Variant Table](#variant-table)), so position is the only way a row can point back at a specific one when an entry has more than one (up to 8 in `sena3.lift`). For `entry-relation`, the same positional keying one level over: the relation's 1-based position among its entry's own `<relation>` siblings — `<relation>` has no id/guid of its own either ([Entry-Relation Table](#entry-relation-table)), and an entry can have up to 3 (`sena3.lift`) |
| `trait_name` | `trait/@name` | required by `trait-content` (no `<optional>` wrapper) — the same required-attribute shape as [Etymology Table](#etymology-table)'s `@type`/`@source` |
| `trait_value` | `trait/@value` | required for the same reason as `trait_name` |

**No column-classification step.** Unlike every other table, `<trait name value>` is already a flat name/value pair rather than a multilingual `<form>`, so there is nothing to pivot into per-language columns, and no reserved-prefix/custom-field-fallback scheme ([Column Classification](#column-classification)) applies here — the six columns above are the whole schema.

**Why a table of its own** rather than columns on the sense/entry table: `lift.rng` wraps `trait` in `<zeroOrMore>` at every attachment point with no schematron cap on repeated `name`s (`trait-content` asserts nothing about uniqueness), and real data already repeats one on every owner — `sena3.lift` has 24 senses with two `semantic-domain-ddp4` traits, 17 with two `Verbo-slot` traits (the latter on one `grammatical-info`, confirmed in `sena3-trait-variety.lift`, curated for this table), one variant with three `environment` traits (confirmed in `sena3-variant-trait-repeated-environment.lift`, extracted from `sena3.lift` entry `89b79930-…`), and one `_component-lexeme` entry-relation repeating `complex-form-type` (confirmed in `sena3-entry-relation-variety.lift`, entry `7725611a-…`, reused from [Entry-Relation Table](#entry-relation-table)'s own fixture). A flat `trait_<name>` column scheme cannot hold any of these.

**Four attachment points, one table.** `sense/trait` (e.g. `semantic-domain-ddp4`, `usage-type`), `sense/grammatical-info/trait` (e.g. `inflection-feature`, and several distinct `*-slot` names), `entry/variant/trait` (`morph-type`, `environment`), and `entry/relation/trait` (`is-primary`, `complex-form-type`, `variant-type`) are structurally distinct locations in the XML, but neither `lift.rng` nor real data ties the `owner` axis to any semantic distinction between trait *kinds* — `sena3.lift`'s `grammatical-info`-owned traits alone span `inflection-feature`, `type`, `from-part-of-speech`, and four different `*-slot` names, each a different kind of fact. `trait_name` is what identifies a trait's meaning; `owner` only says which LIFT element it round-trips through. One table with an `owner` column reuses the identical shape for all four, and is what let `variant` and `entry-relation` each join with no new table, flag, or SPEC.md section — see `plans/remaining-lift-fields.md`'s Decisions to settle for the per-owner-table alternative considered and declined.

**lift2csv direction:** implemented by `trait_table(LIFT_file)` (`R/trait_table.R`), iterated per entry (`.//entry`) rather than with one absolute xpath per owner, so that each entry's variant-owned rows land before its entry-relation-owned ones, which land before its sense/grammatical-info-owned ones, in the output — matching `lift.rng`'s own declared `entry-content` order (`<variant>`, then `<relation>`, then `<sense>`). `extract_sense_traits()` (`R/trait_helpers.R`) reads both `./grammatical-info/trait` and `./trait` for each of that entry's senses, in that order — matching the nesting order real FLEx output uses (`<grammatical-info>` is one of a sense's first children, `<trait>` one of its last, confirmed in every fixture with both); `extract_variant_traits()` reads `./trait` for each of that entry's variants, keyed by the variant's position among its entry's own `<variant>` siblings (mirroring `extract_pronunciation_multitext()`/`extract_reversal_multitext()`'s position-keying one level up); `extract_entry_relation_traits()` does the identical position-keyed read one level over, for `./trait` under each of that entry's own `<relation>` children. Direct-child axes throughout (`./sense`, `./variant`, `./relation`), so this deliberately excludes `sense/subsense/trait`, `sense/subsense/grammatical-info/trait`, `variant/relation/trait`, and `sense/relation/trait` — none occur in any fixture, so widening these axes would be building ahead of real data ([Not Yet Specified](#not-yet-specified)), the same reasoning [Reversal Table](#reversal-table)/[Sense-Relation Table](#sense-relation-table) give for their own identical exclusion of `sense/subsense/reversal`/`sense/subsense/relation`.

**csv2lift direction:** implemented by `attach_traits_to_lift(doc, trait_table)` (`R/csv2lift_trait.R`). For `owner ∈ {sense, grammatical-info}`, a row's `sense_guid` is looked up against `.//sense[@id='...']`; a match failure is a hard error ([Structural Rules](#structural-rules-csv2lift-direction)), never a silently dropped row. For `owner = "sense"`, the `<trait>` is added directly under the sense. For `owner = "grammatical-info"`, it is added under the sense's `<grammatical-info>` element — created on demand with `value=""` if the sense has none, rather than erroring: `sena3.lift` has a sense whose `<grammatical-info value="">` is blank yet still wraps two `<trait>`s (entry `8d3435f5-…`), and [Sense Table](#sense-table)'s "empty optional elements are never emitted" rule already drops that blank-value element on its own when no trait needs it back. This unavoidably positions a lazily-created `<grammatical-info>` after every other sense child already attached by this point (`R/table_registry.R`'s row order), rather than in its canonical first-child position — a readability-only deviation, the same kind [Sense Table](#sense-table) already accepts for `<example>` vs `<note>`.

For `owner = "variant"`, a row's `entry_id` is looked up against `.//entry[@guid='...']` instead (a hard error on no match, same as above), then `owner_index` is looked up against the position of that entry's own `<variant>` children — an `owner_index` that is blank, non-numeric, or outside the range of variants the entry actually has is a hard error, the same "fail fast rather than silently drop" rule [Structural Rules](#structural-rules-csv2lift-direction) already states for foreign keys. `owner = "entry-relation"` works identically, one level over: `entry_id` resolved the same way, then `owner_index` checked against the position of that entry's own `<relation>` children, with the identical hard-error shape on a bad index. `attach_traits_to_lift()` is registered last in `R/table_registry.R`, after `etymologies` — the only attach-order dependency in the registry that is load-bearing rather than cosmetic: a `grammatical-info`-owned row needs `attach_senses_to_lift()`'s sense (and whichever `<grammatical-info>` it already created) to exist first, a `variant`-owned row needs `attach_variants_to_lift()`'s `<variant>` elements to exist first (registered well before `traits`, right after `pronunciations`), and an `entry-relation`-owned row needs `attach_entry_relations_to_lift()`'s `<relation>` elements to exist first (registered right after `reversals`, likewise well before `traits`).

Round-trip spot check against the full `sena3.lift` (168 variants; 31 entry-relations, 23 of them carrying a trait) confirmed lossless: every variant-owned trait recovered identically, including the entry (`89b79930-…`) whose one variant carries three `environment` traits, and the entry (`d7a3eba8-…`) whose one variant has no `<form>` at all and previously round-tripped as an empty `<variant/>` — it now also recovers that variant's `morph-type` trait, closing the gap [Variant Table](#variant-table) left open. All 44 entry-relation-owned trait instances also recovered identically, including entry `7725611a-…`'s repeated `complex-form-type`.

## csv2lift CLI shape

- A single script, not one script per table — a LIFT file requires all tables joined together to build one coherent tree. There is no such thing as a "senses-only" LIFT file.
- Takes one CSV per table; the entry table is required, further tables (senses, etc.) are optional as their round-trip support is implemented. A table can be supplied either as an explicit `--<table>` flag or discovered via `--table-dir <dir>` (below); an explicit flag overrides a discovered file of the same table.
- Internally joins tables by their declared foreign key before building the tree (attaches `<sense>` and `<pronunciation>` children to the `<entry>` whose `guid` matches each row's `entry_id`, and `<example>` children to the `<sense>` whose `id` matches each row's `sense_guid`).
- Currently implemented: `scripts/csv2lift.R` (renamed from `scripts/csv2lift_entry-table.R`), with the entry table supplied as a bare positional argument (kept for backward compatibility) or `--entries`, plus `--senses`, `--pronunciations`, and `--examples` (all optional). The tables are attached in registry order — pronunciations, then senses, then examples — so the emitted child order matches [Entry Table](#entry-table); `--examples` is rejected with a usage error unless `--senses` is also given, since `<example>` attaches to `<sense>` ([Example Table](#example-table)).
- **`R/table_registry.R`** is the single source of truth for which tables exist: each row names a table's CLI flag, its read function, its attach function, the table(s) it requires, and its foreign key. Adding a table to the registry is what makes it available to both scripts below — see `plans/remaining-lift-fields.md`'s Phase T.
- **`--table-dir <dir>` discovers a CSV per table in that directory**, instead of naming each one individually — `<dir>/entries.csv`, `<dir>/senses.csv`, etc., one export per directory (a trailing slash is tolerated but not significant). Any `*.csv` directly in `<dir>` that names no known table is a hard error, not a silently dropped table — see [Structural rules](#structural-rules-csv2lift-direction). The entry table is mandatory: it must be supplied by exactly one of the positional argument, `--entries`, or discovery.
- **`--header-from <lift-file>` copies that file's `<header>/<fields>` verbatim into the output**, as the `<lift>` root's first child (`R/csv2lift_header.R`'s `insert_header_fields_from_lift()`), a plain document-level flag rather than a `table_registry.R` row — it takes a whole LIFT file, not a CSV, and there is nothing to join it against. Only `<fields>` is copied, never `<header>/<ranges>`: FLEx recreates any missing range item on import (adding it to the target project's own list), but a custom `<field>` declaration is the only thing that tells FLEx a custom field's real type (e.g. `MultiUnicode` vs. a plain `String`) instead of defaulting one in — per the FLEx documentation, cited in `plans/remaining-lift-fields.md`'s D2. The block is extracted from the source file's raw text via the same `(?s)<fields>.*?</fields>` regex style `R/copy_lift_entries.R` already uses for `<header>` as a whole, not parsed field-by-field, so it is agnostic to a tag's own content (checked against four real FLEx exports: `<field>` always has exactly a `tag` attribute and one or two `<form lang="en"|"qaa-x-spec"><text>` children, but a tag can itself contain spaces, e.g. `"3SG PFV Form"`, which the verbatim-copy approach never needs to know about). If the source file has no `<fields>` section, a stderr warning is emitted and no `<header>` is written at all — a header-less LIFT file is valid (the FLEx documentation states the `<header>` element itself is optional), so this is not an error.
- **`scripts/lift2csv.R`** is the read-side counterpart, in one of two mutually exclusive modes. `--table-dir <dir>` writes every table the registry knows how to read into `<dir>` as `<name>.csv`, skipping a table entirely when the LIFT file has no rows for it (the entry table's CSV is always written, since it is mandatory — that skip is a row rule, decided before formatting, unrelated to the column rule below). `--table <name>` writes that one table's CSV to stdout instead — an empty table is an empty CSV on stdout here (`""`, not even a header row), rather than an omitted file, since there is no directory listing to omit it from. This zero-byte output is a *consequence* of [Data Handling](#data-handling)'s empty-column rule, not a separate case: a zero-row table has every column blank, so every column prunes and nothing is left to have a header.

## Verification

All claims in this spec are checked by the approval tests under `tests/testthat/` (see `AGENTS.md`'s Testing Approach) — golden `.lift`/`.csv` files under `tests/testthat/_snaps/`, generated from fixtures under `tests/testthat/fixtures/`.

If a test's expected output and this spec disagree, that is a bug in one of them — resolve the disagreement explicitly (don't just edit whichever is more convenient) and update this spec if the resolution changes a stated rule.

## Not yet specified

Deliberately undesigned until actually built, to avoid speculating ahead of development:

- **A `<form lang="x"><text/></form>` with a real `lang` but empty text does not round-trip.** [Data Handling](#data-handling)'s empty-column rule drops a column when every row's value is blank, and an empty `<text/>` reads as `""` the same as an absent one — so that `lang`'s whole column prunes and the `<form>` is lost on the way back. This is the one case the empty-column rule can touch a data-driven column rather than a structural one. No fixture has one (zero empty `<text/>` elements repo-wide), so it is left unhandled rather than defended against.
- Within `<variant>` ([Variant Table](#variant-table)): the optional `@ref` (a variant that points at another entry rather than carrying its own form), variant-level `<field>`, and `<pronunciation>`/`<relation>` children `variant-content` allows. None of these appear in any fixture; `sena3.lift`'s 168 variants are all bare forms with traits. (Variant-owned `<trait>` — `morph-type`, `environment` — is read via the traits table's `owner = "variant"` — [Traits Table](#traits-table).)
- Within `<pronunciation>` ([Pronunciation Table](#pronunciation-table)): the optional nested `<annotation>` child that `field-content`/`trait-content` allow, and the `dateCreated`/`dateModified` attributes `extensible-content` allows on `<pronunciation>` itself. Neither appears in any fixture. (The `<media>`'s own `<label>`, pronunciation-level `<field>` — FLEx's "CV Pattern" and "Tone" — and the `location` trait are now read and written; see [Pronunciation Table](#pronunciation-table).) A pronunciation-level trait name other than `location` is unhandled the same way entry-level traits other than `morph-type` are (see above) — real data (`zhi-flex_lift_2026-09-29.lift`) only ever carries the one trait name, so `extract_single_pronunciation_trait()` looks for it specifically rather than through the long `traits` table.
- **Sibling re-order on distinct attribute-keyed elements** ([Data Handling](#data-handling)): the global first-appearance column order can disagree with a given parent's own element order for custom `<field type>`s and typed `<note type>`s, and csv2lift re-orders to match the column order on round-trip. Real figure: 47 senses in `sena3.lift` hold `<note type="phonology">` before `<note type="sociolinguistics">` locally, but the CSV's global column order (established by whichever type's `(type, lang)` pair first appeared anywhere in the document) puts `note_sociolinguistics_en` first, so all 47 re-emit as `(sociolinguistics, phonology)`. `<field type>` has the identical latent exposure — the CSV column-naming scheme is the same — it has simply never fired on any fixture's field data. Do **not** "fix" this by sorting columns; that would violate the first-appearance rule ([Data Handling](#data-handling)) and only works here because FLEx happens to sort its own typed-note siblings alphabetically.
- **Two `<note>`s of one `type` — or two `<field>`s of one `type` — on the same parent are invalid LIFT, and unhandled.** The cap is schema-guaranteed, not a fixture accident ([Column Classification](#column-classification)), so this is the same class of case as the duplicate `<translation>` below rather than a shape the CSV declines to model; no fixture has one at any level (entry, sense, or example). Should it occur it is **not** caught, and fails worse than the duplicate-`<translation>` and duplicate-`<media>` paths, which warn and keep the first: the `(entry_id, type, lang)` key collides in `pivot_wider`, which emits only tidyr's generic "Values … are not uniquely identified; output will contain list-cols" warning, and the resulting list-column then writes as a **blank cell** — losing both values rather than one.
- **A duplicate `<translation>` on one `<example>` loses the second one.** `lift.rng`'s own schematron on `translation-content` asserts "Translations should be of different types", so this is invalid LIFT that FLEx emitted rather than a shape being declined; it occurs once in `sena3.lift` (entry `d5cb3ce5-…`), and `extract_example_translation()` ([Example Table](#example-table)) warns on stderr and keeps only the first.
- Entry-level traits other than `morph-type` (e.g. `environment`, `dialect-labels`), and the entry `dateDeleted` attribute.
- Within `<subsense>` ([Sense Table](#sense-table)): `sense/subsense/reversal`, `sense/subsense/relation`, `sense/subsense/trait`, and `sense/subsense/grammatical-info/trait` all remain unread — none occur in any fixture ([Reversal Table](#reversal-table), [Sense-Relation Table](#sense-relation-table), [Traits Table](#traits-table) each give the identical reasoning for their own exclusion). Nesting a subsense inside another subsense (depth 2+) is permitted by `lift.rng` and the read/write code is generic enough to handle it, but is untested against any fixture — `sena3.lift`'s 8 subsenses are all exactly one level deep. A sense combining its own `<subsense>` with a `sense/relation` is likewise untested, and the two features' independently-correct ordering rules interact in a way that pulls `<example>` ahead of `<relation>` too, not just ahead of `<subsense>`, when combined — see [Sense Table](#sense-table)'s own note on this. Also the sense `dateCreated`/`dateModified` attributes `extensible-content` allows — unlike `@order` ([Sense Table](#sense-table)), these appear on no sense in any fixture, so there is nothing to build against.
- Within `<relation>` ([Entry-Relation Table](#entry-relation-table), [Sense-Relation Table](#sense-relation-table)): `relation/field` and the optional `<usage>` child `relation-content` allows. Neither occurs in any fixture. `entry/relation/trait` is read via the [Traits Table](#traits-table)'s `owner = "entry-relation"` — see the `<trait>` bullet below; `sense/relation/trait` remains unread (it does not occur in any fixture).
- Within `<trait>` ([Traits Table](#traits-table)): traits owned by `sense/relation` (`owner_index` is reserved for this, alongside `variant`/`entry-relation` which now use it) and the optional nested `<annotation>` child `trait-content` allows. Neither occurs in any fixture — `sense/relation` never carries a trait in `sena3.lift`'s 44 sense-relations, unlike `entry/relation`, whose own traits are now read (see above). The `<annotation>` case occurs in no fixture either.
- Within `<reversal>` ([Reversal Table](#reversal-table)): the optional nested `<main>` (FLEx's reversal-index parent hierarchy — a reversal can itself have a parent reversal, recursively, via `reversal-main`), and the optional `<grammatical-info>` a reversal may carry independently of its sense's own. Neither appears on any `<reversal>` in any fixture.
- Within `<example>` ([Example Table](#example-table)): example-level `<field>`/`<trait>`/`<annotation>` children and the `dateCreated`/`dateModified` attributes `extensible-content` allows. None of these appear in any fixture.
- Inline `<span lang>` markup ([Data Handling](#data-handling)) is preserved except for: a span attribute other than `lang` (dropped), a nested span (would not round-trip), and ordinary text that itself contains a literal `<span lang="…">…</span>` string (turned into real markup on the way back). None of these occur in any fixture.
- Patch-in-place / merge-into-existing-LIFT mode for csv2lift.
